# Code Logic Analyzer

**IRON LAW**: 永远向下追踪，不要中途停止。从入口方法开始，追踪每一个方法调用直到Repository层的SQL操作，遇到参数控制/配置逻辑也必须分析。不完整的分析比没有分析更危险。

## 参数系统

分析时可指定以下参数（通过 $ARGUMENTS 传入）：

| 参数 | 说明 | 默认值 |
|------|------|--------|
| `--entry <method/class>` | 指定分析入口 | 当前选中代码或用户指定 |
| `--depth <level>` | 分析深度: `service`/`domain`/`repository`/`full` | `full` |
| `--output <format>` | 输出格式: `text`/`mermaid`/`both` | `both` |
| `--focus <area>` | 重点关注: `logic`/`data`/`error`/`all` | `all` |

## 工作流

```
代码逻辑分析进度：

- [ ] Step 1: 确定分析入口 ⚠️ REQUIRED
  - [ ] 1.1 识别入口方法/类/文件
  - [ ] 1.2 确认分析范围和深度
- [ ] Step 2: 收集代码上下文 ⛔ BLOCKING
  - [ ] 2.1 读取入口代码
  - [ ] 2.2 识别所有直接调用的方法
  - [ ] 2.3 递归追踪间接调用（到Repository层）
- [ ] Step 3: 分析业务逻辑
  - [ ] 3.1 分析条件分支和业务规则
  - [ ] 3.2 追踪数据流转和变换
  - [ ] 3.3 识别异常处理和边界情况
  - [ ] 3.4 分析参数控制/配置逻辑（如有）
- [ ] Step 4: 生成分析报告
  - [ ] 4.0 先用自然语言总结业务流程 ⚠️ FIRST
  - [ ] 4.1 生成结构化文本报告
- [ ] Step 5: 输出交付
```

## Step 1: 确定分析入口 ⚠️ REQUIRED

### 1.1 识别入口

入口类型及识别方式：

| 入口类型 | 如何识别 | 示例 |
|---------|---------|------|
| 选中的方法 | 用户选中的代码片段 | `borrowBook(userId, bookId)` |
| Controller接口 | `@RequestMapping`/`@GetMapping`等注解 | `POST /api/borrow` |
| 指定类/文件 | 用户明确指定的类名或文件路径 | `BorrowAppService.java` |

### 1.2 确认范围

向用户确认（如果不明确）：
- 分析到哪一层停止？（默认：到Repository层SQL）
- 是否需要分析关联的配置/参数控制？（默认：是）
- 输出格式偏好？（默认：文本 + Mermaid）

---

## Step 2: 收集代码上下文 ⛔ BLOCKING

此步骤必须完成才能进行分析。

### 2.1 读取入口代码

使用 `read_file` 或 `grep_code` 读取入口方法所在文件。

### 2.2 识别直接调用

从入口方法开始，识别所有被调用的方法：

**问自己**：
- 这个方法调用了哪些其他方法？
- 调用的是哪个类的方法？（注意接口和实现类的关系）
- 有没有通过依赖注入调用的服务？

### 2.3 递归追踪调用链

按以下顺序追踪，直到到达终点：

```
Controller → AppService → DomainService → Repository → Mapper(SQL)
                ↓              ↓               ↓
           Convert层      Entity/VO       PO转换
```

**追踪规则**：
1. 遇到接口时，找到对应的实现类
2. 遇到Mapper接口时，找到对应的XML文件中的SQL
3. 遇到参数查询/配置读取时，追踪配置来源
4. 遇到外部服务调用时，记录调用点但不深入（标注为外部依赖）

**停止条件**：
- 到达Mapper层的SQL语句
- 到达外部系统调用边界
- 到达JDK/框架原生方法

---

## Step 3: 分析业务逻辑

### 3.1 分析条件分支和业务规则

**识别并记录**：
- `if/else` 条件判断及其业务含义
- `switch/case` 逻辑分支
- 三元运算符中的业务判断
- 循环中的筛选/过滤逻辑
- 提前返回（early return）的条件

**问自己**：
- 每个分支代表什么业务场景？
- 有哪些边界条件会触发特殊处理？
- 业务规则是硬编码还是可配置的？

### 3.2 追踪数据流转

**记录数据变换路径**：

```
请求参数 → DTO → Entity/Domain Object → PO → 数据库字段
                     ↓
              业务计算/转换
```

**关注点**：
- 字段映射关系（哪些字段被映射到哪里）
- 数据转换逻辑（Convert类中的转换规则）
- 数据聚合/计算（业务计算逻辑）
- 默认值处理

### 3.3 识别异常处理

**记录**：
- 显式抛出的异常及条件
- 校验失败的处理
- 事务回滚条件
- 全局异常处理器的处理逻辑

### 3.4 分析参数控制（如有）

如果代码中涉及：
- 参数表查询
- 配置文件读取
- 开关/特性标志

需要追踪：
- 参数名称和取值范围
- 参数如何影响业务流程
- 默认值和回退策略

## Step 4: 生成分析报告

### 4.0 自然语言流程总结 ⚠️ FIRST

**在输出任何结构化报告之前，必须先用自然语言描述整个业务流程。**

使用"先...然后...接着...最后..."的叙述方式，像讲故事一样描述代码做了什么：

**示例格式**：
```
当用户发起XXX请求时，系统会按以下步骤处理：

1. 首先，检查XXX
   系统先看看有没有传XXX参数，如果没传，直接返回错误。

2. 然后，查询XXX
   根据XXX去数据库查这条记录存不存在：
   - 如果查不到，抛出异常："XXX不存在"
   - 如果查到了，但状态不对，抛出异常："XXX状态异常"

3. 接着，执行XXX操作
   ...

4. 最后，返回结果
   把处理结果转成DTO，返回给前端。
```

**要求**：
- 用口语化的表达，避免技术术语堆砌
- 按时间顺序描述"先干嘛、再干嘛、然后干嘛"
- 每个步骤说明做什么、为什么、失败会怎样
- 可以在最后加一句简化版的一句话流程总结

## 反模式 ❌

**不要这样做**：

1. **跳过自然语言总结**：直接输出表格和技术细节，不先用通俗语言描述流程
2. **半途而废**：分析到Service层就停止，不追踪到SQL
3. **忽略实现类**：只看接口定义，不找实现类代码
4. **跳过转换层**：不分析Convert类中的字段映射
5. **假设而非验证**：猜测某个方法的作用而不去读代码
6. **忽略配置**：不追踪参数表/配置对业务的影响
7. **纯罗列代码**：只贴代码不解释业务含义
8. **遗漏异常路径**：只分析正常流程，忽略异常分支

## 快速参考

### DDD项目分层（本项目结构,仅供参考。以实际项目目录为准）

```
adapter/controller/     → 接口层（Controller）
application/service/    → 应用服务层（编排业务流程）
application/dto/        → 数据传输对象
application/convert/    → DTO-Entity转换
domain/model/entity/    → 领域实体
domain/model/valueobject/ → 值对象
domain/service/         → 领域服务（核心业务逻辑）
domain/support/         → 仓储接口
infrastructure/repository/impl/    → 仓储实现
infrastructure/repository/mapper/  → MyBatis Mapper接口
infrastructure/repository/po/      → 持久化对象
infrastructure/repository/convert/ → PO-Entity转换
resources/mapper/       → MyBatis XML（SQL定义）
```

### 常见调用模式

```
[Controller]
    ↓ 调用
[AppService] → 使用 [Convert] 转换 DTO→Entity
    ↓ 调用
[DomainService] → 处理核心业务逻辑
    ↓ 调用
[Repository接口] → 通过 [RepositoryImpl] 实现
    ↓ 调用
[Mapper接口] → 对应 [Mapper.xml] 中的SQL
```
